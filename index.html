envelop-letterbox wraps every API response in an AES-GCM encrypted, HMAC-signed envelope. Plaintext JSON disappears from browser DevTools. Curl-based scrapers stop working. MITM tampering gets caught. Your route handlers stay exactly as they are.

The problem

Open DevTools. See your data. So does everyone else.

Every API response you ship lands in the browser's Network tab as readable JSON. Your field names, data shapes, IDs, pricing, and business logic are one F12 away from any user, support rep, corporate proxy, or scraper with a curl command.

HTTPS protects data in transit. It does nothing once the browser receives it. That's the gap this library fills.

Without envelop-letterbox
// Browser Network tab → Response

{
  "users": [
    { "id": 1,
      "name": "Alice",
      "plan": "enterprise",
      "mrr": 4200 },
    { "id": 2,
      "name": "Bob",
      "plan": "free" }
  ],
  "total": 2
}
With envelop-letterbox
// Browser Network tab → Response

{
  "v": 1,
  "sid": "a3f8c2...",
  "n": "7d4e1a...",
  "ct": "U2FsdGVkX1+mK8...",
  "sig": "c3ab8f..."
}

// Your app code still gets:
// { users: [...], total: 2 }
Honest disclaimer: This is not cryptographic security against the end user. Someone who opens DevTools and sets a breakpoint inside the library can still read decrypted data — that's an unsolvable property of running JavaScript in a browser. What this does do: raise the scraping cost from "5 seconds with curl" to "you need to execute my JS", deter casual inspection, and prevent MITM response tampering. If data must be hidden from the user entirely, keep it server-side.

Internals

How it works

The whole flow runs automatically. You do not touch any of it.

ECDH Handshake (first request)

Client and server each generate ephemeral P-256 keypairs and exchange public keys. Both sides derive the same AES-GCM encryption key and HMAC signing key via HKDF. The raw key is never sent over the wire.

Encrypted + signed envelope

Every subsequent response body is encrypted with AES-GCM and HMAC-signed (separate key, same HKDF). The wire format is a compact JSON object: { v, sid, n, ct, sig }.

Transparent decryption on the client

The createTransport client decrypts and verifies every response before returning it. Your UI code calls api.get('/users') and gets plain JS objects. No glue code needed.

Session expiry + auto re-handshake

Sessions expire after 1 hour by default. On expiry (or server restart), the client re-handshakes automatically and retries the request once. Fully transparent.

Getting started

Quickstart

Two steps. Add the middleware on the server. Use the transport on the client. Done.

1 — Server (Express)

server.js
import express from 'express';
import { createGuard } from 'envelop-letterbox/server/express';

const app = express();
app.use(express.json());
app.use(createGuard());  // ← one line, zero config

app.get('/users', (req, res) => {
  res.json({ users: [/* ... */] });  // ← unchanged, auto-encrypted
});

app.listen(3000);

2 — Client (browser or Node)

client.js
import { createTransport } from 'envelop-letterbox/client';

const api = createTransport({ baseURL: 'http://localhost:3000' });

const data = await api.get('/users');
// data === { users: [...] }  ← decrypted, verified, ready to use

// All methods available:
await api.post('/users', { name: 'Charlie' });
await api.put('/users/1', { plan: 'pro' });
await api.delete('/users/1');

That is the entire integration. Route handlers don't change. UI data-fetching doesn't change.

Skipping specific routes

server.js — skip health checks and public routes
app.use(createGuard({
  skipPaths: ['/health', '/public', /^\/assets\//]
}));

Custom session store (Redis, multi-instance)

server.js — plug in Redis for clustered deployments
class RedisSessionStore {
  async get(sid)      { /* fetch + deserialize from Redis */ }
  async set(session)  { /* serialize + store with TTL    */ }
  async delete(sid)   { /* DEL                           */ }
}

app.use(createGuard({ sessionStore: new RedisSessionStore() }));

Note: CryptoKey is not JSON-serializable. Store raw key bytes and re-import on read. A reference Redis implementation ships in a future release.

Reference

API

createTransport(options) — client

Creates an HTTP client that transparently handles handshakes, encryption, and decryption.

Option Default Description
baseURL required Base URL of the server.
handshakeEndpoint /__envelope/handshake Path the server listens on for key exchange.
fetchOptions {} Extra options applied to every fetch call (credentials, headers, etc.).
debug false Log handshake and request events to the console.
fetch global fetch Supply a custom fetch implementation (e.g. node-fetch, undici).

Returns: { get, post, put, patch, delete, request, rotateSession }

createGuard(options) — Express middleware

Drop-in Express middleware. Handles the handshake endpoint and encrypts all non-skipped responses.

Option Default Description
handshakeEndpoint /__envelope/handshake Path that handles the ECDH key exchange.
sessionTtlMs 3600000 (1h) How long a derived session key lives before expiry.
sessionStore in-memory Map Implement the SessionStore interface for Redis or any external store.
skipPaths [] Strings or RegExps for paths to bypass (e.g. /health, public assets).

FAQ

Frequently asked questions

Is this actually secure?
It's designed to be opaque, not secure against the user. Read the threat model above. If you need real protection from the end user, keep that data server-side. This is not a substitute for proper authorization.
Why not just minify or obfuscate JavaScript?
Obfuscation hides your code. This hides the data shape and values flowing over the wire. Even with fully readable JS, a scraper now has to run your whole client instead of hitting an endpoint with curl.
Does it work in Node-to-Node (server-to-server)?
Yes. The transport works in any environment with the WebCrypto API — Node 18+, Bun, Deno, browsers, and Edge Workers.
Does it work with streaming responses (SSE, chunked transfer)?
Not in v0.1. Streaming requires a different protocol design. Use plain HTTPS for those endpoints and add them to skipPaths.
What about file uploads (multipart)?
Multipart request bodies are not envelope-wrapped in v0.1. Other fields pass through normally.
Can I encrypt only some routes?
Yes. Use skipPaths in createGuard to exclude paths from encryption. The client sends a session header on every request; non-guarded routes ignore it silently.
How do I debug what the encrypted envelope actually looks like?
Pass debug: true to createTransport for client-side logs. On the server, log inside your own route handler — the plaintext is available there as normal.
